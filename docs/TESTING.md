# 테스트 규칙

새 코드와 수정 코드에 적용하는 테스트 기준입니다. `현재`로 표시하지 않은 항목은 [ROADMAP.md](ROADMAP.md)에 따라 도입할 목표입니다.

## 1. 실행 방법

```bash
./gradlew test
```

- CI는 `./gradlew clean test`를 실행합니다. (현재)
- 현재 테스트 DB는 H2(MySQL 호환 모드)입니다.
- Testcontainers 도입 후에는 통합 테스트에 Docker가 필요합니다.

## 2. 테스트 종류와 사용 기준

| 종류 | 도구 | 검증 대상 | 쓰지 말아야 할 때 |
| --- | --- | --- | --- |
| 도메인 단위 | JUnit | 상태 전이, 금액 계산 | - |
| 서비스 단위 | JUnit, Mockito | 분기, 예외, 포트 호출 | 락, 트랜잭션, 쿼리 검증 |
| 리포지토리 | `@DataJpaTest`, Testcontainers | QueryDSL, JPQL, 락 쿼리 | 비즈니스 분기 검증 |
| 컨트롤러 | `@WebMvcTest` | 입력 검증, 응답 형식, 인가 | 비즈니스 로직 검증 |
| 통합 | `@SpringBootTest`, Testcontainers | 트랜잭션, 분산 락, 전체 흐름 | 단순 분기 검증 |
| 구조 | `ModularitySmokeTest` | 모듈 경계 (현재) | - |
| 부하 | JMeter 또는 k6 | 처리량, 응답 시간 | PR마다 실행 |

## 3. 기본 규칙

1. 동작을 바꾸면 테스트도 함께 바꿉니다.
2. 버그를 고칠 때는 수정 전에 실패하는 회귀 테스트를 먼저 작성합니다.
3. 동시성, 락, 트랜잭션, 쿼리 동작은 mock으로 검증했다고 보지 않습니다. 실제 DB를 사용합니다.
4. 락 동작은 H2로 검증하지 않습니다. 운영과 같은 MySQL 8.0을 사용합니다.
   - AOP 순서, 조건부 빈, 비동기 이벤트는 실제 스프링 컨텍스트에서만 드러나므로 `ApplicationIntegrationTest`에서 함께 검증합니다.
5. 테스트가 깨졌을 때 기대값을 고치려면, 동작 변경이 의도된 것인지 먼저 확인합니다.
6. `@Disabled`와 스킵에는 이유와 추적 항목을 적습니다.
7. 시간과 난수에 의존하는 값은 고정해서 재현 가능하게 합니다.
8. 동시성 테스트의 대기에 `Thread.sleep`을 쓰지 않고 `CountDownLatch` 등으로 시작 시점을 맞춥니다.
9. 외부 PG는 자동 테스트에서 호출하지 않습니다. `PortOnePaymentClient` 경계에서 대체합니다. 실제 테스트 채널 검증은 `PortOneLivePaymentFlowTest`를 수동으로 실행하며, 지정한 결제 건을 실제로 취소합니다.
10. `ModularitySmokeTest`의 기준을 완화할 때는 커밋 메시지에 이유를 적습니다.

## 4. 작성 형식

- 클래스 이름: `대상클래스Test`, 통합 테스트는 `대상기능IntegrationTest`
- 위치: 대상 클래스와 같은 패키지 구조
- 이름: `메서드_상황_기대결과`, 또는 한글 `@DisplayName("기능: 상황이면 결과")`
- 구조: 준비, 실행, 검증 순서로 작성하고 한 테스트에는 하나의 동작만 검증합니다.
- 예외 검증: 예외 타입만 보지 말고 `errorCode`까지 확인합니다.

```java
assertThatThrownBy(() -> orderService.purchaseConfirmation(memberId, orderId))
        .isInstanceOf(BusinessException.class)
        .extracting("errorCode")
        .isEqualTo(BusinessErrorCode.ORDER_CANNOT_CONFIRM);
```

## 5. 필수 시나리오

아래 시나리오는 CI에서 항상 통과해야 합니다. 체크되지 않은 항목은 **기존 테스트와 대조 전이거나 아직 구현되지 않은 목표**이며, 확인하면 체크합니다.

### 재고

- [x] 재고 N개 상품에 N+α건 동시 주문: 성공 N건, 최종 재고 0
- [x] 주문과 취소 동시 실행: 최종 재고 = 초기 재고 - 유효 주문 수량 (R-03)
- [x] 관리자 재고 수정과 주문 동시 실행: 주문 차감 유실과 데드락 없음, 읽은 뒤 재고가 변했으면 거부 (R-24)
- [x] 여러 옵션을 서로 다른 순서로 담은 동시 주문: 데드락 없이 완료

### 포인트·쿠폰

- [x] 같은 회원의 동시 주문: 포인트 초과 사용 없음
- [x] 같은 쿠폰으로 동시 주문: 1건만 성공
- [x] 취소 시 포인트와 쿠폰이 한 번만 복원됨
- [x] 한정 쿠폰 동시 발급: 발급 수량 초과 없음, 회원당 1장

### 결제

- [x] 같은 결제의 검증 요청 동시 실행: 한 번만 결제 완료 처리
- [x] 금액 또는 거래 ID 불일치: 거부되고 상태 변화 없음
- [x] 다른 회원의 결제 접근: 거부
- [x] PG 결제 완료 후 확인 요청 없이 취소 시점 도달: 돈만 받은 상태로 끝나지 않음 (R-01)
- [x] 취소된 주문의 결제 대사: PG 취소까지 완료

### 환불

- [x] 승인되지 않은 환불 거부
- [x] 같은 결제의 환불 요청 동시 실행: PG 취소 한 번, 복원 한 번
- [x] PG 취소 타임아웃: 상태가 잘못 확정되지 않음 (R-05)
- [x] 주문 보정 실패: 복구 큐에 한 건만 적재 (R-04)
- [x] 복구 반복 실패: 최대 횟수 후 DLQ로 이동 (R-04)

### 권한

- [x] 관리자 API에 일반 회원 접근 거부
- [x] 다른 회원의 주문, 결제, 장바구니, 리뷰 접근 거부 (주문·결제는 실제 HTTP, 리뷰는 서비스 테스트, 장바구니는 API가 로그인 회원 기준)
- [x] 채팅방 비참여자의 구독 거부
- [x] `/topic/*` 등 패턴 구독 거부 (R-02)
- [x] `/topic`으로 직접 `SEND` 거부 (R-02)

### 인증

- [x] 만료·위조 토큰 거부, access와 refresh 토큰 혼용 거부
- [x] 재발급 후 이전 refresh 토큰 거부
- [x] 비밀번호 변경, 정지, 탈퇴 후 재발급 거부
- [x] 로그인 실패 응답으로 계정 존재와 상태를 알 수 없음 (R-23)
- [x] 로그아웃 후 refresh 토큰 거부

## 6. 커버리지 기준

JaCoCo로 측정합니다. 리포트는 `build/reports/jacoco/test/html/index.html`에 생성됩니다.

- **CI 하한 (현재 적용):** 전체 라인 85%, 분기 65%. 2026-11-02 측정값(라인 89.7%, 분기 72.5%) 기준이며, 이 아래로 내려가면 CI가 실패합니다.
- **목표:** 아래 표의 수치입니다. **도입 후 조정 가능한 초기 가정치**이며 아직 CI에 적용하지 않았습니다. 테스트가 늘어나는 대로 하한을 올립니다.

| 범위 | 라인 | 분기 |
| --- | --- | --- |
| `payment`, `order` 서비스·도메인 | 85% | 75% |
| `coupon`, `member`, `security` | 75% | 65% |
| 전체 | 70% | - |

- 수치 달성보다 5절의 시나리오 통과를 우선합니다.
- 전체 수치를 낮추는 PR은 이유를 남깁니다.
- DTO, QueryDSL 생성 클래스, 설정 클래스는 측정에서 제외합니다.

## 7. CI 기준

| 단계 | 내용 | 실패 시 | 도입 |
| --- | --- | --- | --- |
| 시크릿 스캔 | gitleaks | 병합 불가 | 현재 |
| 단위·구조 테스트 | `./gradlew test` | 병합 불가 | 현재 |
| 통합 테스트 | Testcontainers, 실행 여부 검사 | 병합 불가 | 현재 |
| 커버리지 | JaCoCo 하한 검사 | 병합 불가 | 현재 |
| 알림 규칙 | `promtool test rules` | 병합 불가 | 현재 |
| 의존성 스캔 | Dependabot 경고 확인 | Critical은 병합 전 판단 | 2단계 |
| 부하 테스트 | 스테이징에서 수동 또는 예약 실행 | 출시 불가 | 4단계 |

## 8. 코드 리뷰 체크리스트

- [ ] 동작 변경에 맞는 테스트가 있는가
- [ ] 락이 필요한 수정에 실제 DB 테스트가 있는가
- [ ] 외부 호출이 트랜잭션 밖에 있는가
- [ ] 재시도해도 안전한가 (멱등성)
- [ ] 다른 회원의 데이터에 접근할 수 없는가
- [ ] DB 스키마 변경에 마이그레이션 스크립트가 포함되었는가
- [ ] 새 위험을 [RISK_REGISTER.md](RISK_REGISTER.md)에 기록했는가

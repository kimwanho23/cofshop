# 쿠폰 발급: Redis Stream에서 RabbitMQ로 전환

쿠폰 발급 구조를 Redis Stream에서 DB 직접 처리와 RabbitMQ 이벤트 발행으로 바꾼 이유를 정리한 문서입니다.

- **상태:** 전환 완료. Redis Stream 코드는 2026-11-01에 제거했습니다.
- **관련 커밋:** `c54792b`(Stream 도입, 2025-07-07), `3b92135`(RabbitMQ·outbox 추가, 2026-02-15), `c98dd58`(Stream 적재 코드 제거, 2026-02-16)
- **이유의 근거:** 당시 커밋 메시지에 이유가 남아 있지 않습니다. 아래 전환 이유는 두 구조의 코드 차이에서 정리한 내용입니다.

## 요약

Redis Stream을 RabbitMQ로 그대로 바꾼 것이 아닙니다. **발급 처리**와 **발급 후 알림**의 역할을 나눴습니다.

| 역할 | 이전 | 현재 |
| --- | --- | --- |
| 발급 처리 | Stream 컨슈머가 비동기로 처리 | 요청 안에서 DB가 동기로 처리 |
| 수량·중복 제어 | Redis Lua 스크립트, DB | DB 조건부 UPDATE, 유니크 제약 |
| 발급 후 이벤트 | 없음 | outbox를 거쳐 RabbitMQ로 발행 |
| 실패 메시지 처리 | 직접 구현한 Pending 정리, DLQ 소비자 | RabbitMQ DLX·DLQ |

## 이전 구조

```text
발급 요청 → Stream 적재 → (응답) → 컨슈머 3개 → Redis 수량·중복 확인 → DB 저장
                                      └ 실패 → Pending 정리 → 재시도 → DLQ
```

## 현재 구조

```text
발급 요청 → 트랜잭션 시작
             ├ 수량 차감 (조건부 UPDATE, 수량이 없으면 실패)
             ├ 회원 쿠폰 저장 (유니크 제약으로 1인 1장)
             └ outbox 이벤트 저장
           커밋 → (응답)

outbox 스케줄러 → RabbitMQ exchange → queue (실패 시 DLX → DLQ)
```

## 전환 이유

**1. 발급 결과를 바로 알려 줄 수 있습니다.**
Stream 방식은 요청 접수만 응답하므로, 품절이나 중복을 고객에게 바로 알려 줄 수 없었습니다. 지금은 같은 요청에서 성공 또는 실패를 응답합니다.

**2. 수량의 기준이 DB 하나로 줄었습니다.**
이전에는 Redis와 DB에 수량이 따로 있어 DB 저장이 실패하면 Redis를 되돌려야 했고, Redis 수량이 초기화되기 전의 요청(`STOCK_NOT_INITIALIZED`)도 따로 처리해야 했습니다.

**3. 재처리 코드를 직접 관리하지 않아도 됩니다.**
Stream에서는 ACK 안 된 메시지 회수, 재시도 횟수 관리, DLQ 이동과 감시를 모두 직접 구현했습니다(`PendingMessageCleaner`, `CouponDlqConsumer`, 모니터 2개). RabbitMQ는 확인 응답과 DLX를 브로커 기능으로 제공합니다.

**4. DB 저장과 이벤트 발행이 어긋나지 않습니다.**
이벤트를 DB 트랜잭션 안에서 outbox에 함께 저장하므로, 발급은 됐는데 이벤트가 사라지는 일이 없습니다. 발행이 실패하면 재시도하고, 횟수를 넘으면 `FAILED`로 남겨 알림을 보냅니다.

## 대가와 주의할 점

- **선착순 부하:** 요청마다 쿠폰 행을 DB에서 잠그고 수정합니다. 인기 쿠폰에 요청이 몰리면 Stream보다 먼저 병목이 될 수 있습니다. 부하 테스트로 확인해야 합니다.
- **소비자가 없음:** 이 저장소에는 RabbitMQ 큐를 읽는 코드가 없습니다. `coupon.rabbit.enabled=true`로 켜면 소비자가 생기기 전까지 큐에 메시지가 쌓입니다.
- **기본값은 RabbitMQ를 쓰지 않음:** 기본 설정(`coupon.rabbit.enabled=false`)에서는 이벤트를 로그로만 남기고 발행 완료로 표시합니다. 이벤트가 필요해지면 소비자를 만들고 설정을 켜야 합니다.
- **중복 전달 가능:** outbox는 최소 한 번 전달입니다. 발행 후 커밋 전에 장애가 나면 같은 이벤트가 다시 발행되므로, 소비자는 `outboxEventId`로 중복을 걸러야 합니다.
- **운영 구성 추가:** RabbitMQ를 켜면 브로커 운영과 모니터링이 필요합니다.

## 다시 검토할 조건

- 부하 테스트에서 쿠폰 행 잠금이 목표 수치를 막으면, DB 앞단에서 수량을 먼저 거르는 구조를 검토합니다.
- 발급 이벤트를 쓰는 기능(알림, 통계 등)이 계획에 없으면, RabbitMQ와 outbox를 유지할지 다시 판단합니다.

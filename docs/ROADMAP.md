# 실서비스 전환 로드맵

cofshop을 실제 운영 가능한 수준으로 만들기 위한 목표, 단계별 작업, 완료 기준을 정리한 문서입니다.

- 작성일: 2026-10-31
- 위험 항목의 상세 내용: [RISK_REGISTER.md](RISK_REGISTER.md)
- 테스트 기준: [TESTING.md](TESTING.md)

## 1. 목표 수치

아래 값은 **모두 가정치**입니다. 실제 사업 규모가 정해지면 수정하고, 수정하면 2단계·4단계의 기준도 함께 조정합니다.

| 항목 | 가정치 |
| --- | --- |
| 동시 접속 사용자 | 1,000명 |
| 주문 생성 처리량 | 평시 5 TPS, 피크 50 TPS |
| 응답 시간 (p95) | 조회 300ms 이하, 주문 생성 1초 이하 |
| 오류율 (피크 부하) | 1% 이하, 결제·재고 정합성 오류 0건 |
| 가용성 | 월 99.9% |
| 복구 목표 | RPO 5분, RTO 1시간 |

## 2. 현재 상태 요약

- 기능: 회원, 상품, 장바구니, 주문, 쿠폰, 결제, 채팅, 통계 구현됨
- 테스트: 447건 통과(1건 스킵). 대부분 Mockito 단위 테스트이며 실제 DB·동시성 검증 없음
- 결함: 위험도 높은 항목 5건 미해결 (R-01 ~ R-05)
- 운영 기반: DB 마이그레이션 도구, 메트릭, 알림, 활성화된 배포 파이프라인 없음
- 의존성: Spring Boot 3.5.16 업그레이드를 `main`에 반영함 (커밋 `9ffc3b8`). 남은 취약점은 R-13 참고

## 3. 단계별 계획

단계는 순서대로 진행합니다. 완료 기준을 모두 만족해야 다음 단계로 넘어갑니다.

### 0단계: 현재 작업 정리

- [ ] 작업 트리의 미커밋 변경을 주제별로 나눠 커밋
- [x] 의존성 업그레이드를 별도 커밋으로 반영
- [x] GitHub 보안 경고 재확인 (남은 5건 dismiss, R-13 참고)
- [ ] `node_modules/`를 `.gitignore`에 추가
- [ ] 현재 코드와 다른 문서 수정 (`PROJECT_OVERVIEW.md`, `README.md`의 Elasticsearch, iamport, ddl-auto, 템플릿 파일 안내)

**완료 기준:** `main`에서 CI가 통과하고, GitHub의 Critical 경고 목록을 R-13과 대조해 기록함

### 1단계: 결함 제거

- [ ] R-02 채팅 구독·전송 권한 수정
- [ ] R-03 재고 복구·수정 시 락 적용
- [ ] R-04 환불 복구 큐 중복 적재 수정
- [ ] R-06 `OrderItem` 빌더 중복 제거
- [ ] Testcontainers(MySQL, Redis) 기반 통합 테스트 환경 구축
- [ ] R-07 ~ R-10 정책 결정 후 반영 (5절 참고)

**완료 기준:** 위 항목마다 수정 전에 실패하던 회귀 테스트가 존재하고, [TESTING.md](TESTING.md)의 재고·채팅 필수 시나리오가 통과함

### 2단계: 운영 기반 구축

- [ ] Flyway 도입, 기존 `docs/sql`·`docs/db` 스크립트를 기준 스키마로 통합 (R-11)
- [ ] Actuator, Micrometer, 메트릭 수집 구성 (R-12)
- [ ] 핵심 지표 알림: 5xx 비율, 응답 시간, 복구 큐·DLQ 크기, Redis Stream 지연
- [ ] 구조화 로그와 요청 추적 ID, 로그의 개인정보 마스킹 점검
- [ ] JaCoCo 커버리지 측정과 CI 기준 적용
- [ ] CI에 통합 테스트 단계 추가
- [ ] DB 백업과 복구 절차 수립, 복구 리허설 1회

**완료 기준:** 빈 DB에서 Flyway만으로 스키마가 생성되어 `ddl-auto=validate`로 기동되고, 의도적으로 낸 장애에 알림이 도착하며, 백업에서 복구한 결과가 RPO·RTO 가정치를 만족함

### 3단계: 결제 안정화

- [ ] PortOne webhook 또는 대사 스케줄러 설계 (R-01, R-05 공통 해결)
- [ ] 자동 취소 전에 PG 상태를 조회하도록 변경
- [ ] 환불 취소 결과가 불확실할 때 `PAID`로 되돌리지 않고 대사로 확정
- [ ] 결제 불일치 조회와 수동 처리용 관리자 기능
- [ ] 결제·환불 장애 대응 절차 문서화
- [ ] PortOne 테스트 채널로 결제, 취소, 부분 실패 시나리오 검증

**완료 기준:** 브라우저 이탈, PG 타임아웃, 앱 재시작 상황에서 사람의 개입 없이 PG와 DB 상태가 일치하게 되며, 불일치가 생기면 알림이 옴

### 4단계: 규모 검증과 출시 준비

- [ ] 스테이징 환경 구축, CI deploy 잡 활성화
- [ ] 배포와 롤백 리허설 (마이그레이션 포함)
- [ ] 주문·결제·조회 혼합 시나리오로 부하 테스트, 피크 2배 스파이크 포함
- [ ] 병목 개선과 커넥션 풀, 락 대기 시간 조정
- [ ] 다중 인스턴스 동작 검증 (스케줄러, 분산 락, WebSocket simple broker 한계)
- [ ] 보안 점검: 의존성 스캔, 인증·인가, 관리자 API, 파일 업로드
- [ ] 미검토 영역 코드 점검 (R-18)

**완료 기준:** 1절의 목표 수치를 스테이징에서 만족하고, 부하 중 재고·포인트·쿠폰·결제 정합성 검사가 0건 오류이며, 높음 등급 위험이 모두 해결 또는 수용 결정됨

## 4. 출시 판단 기준

아래를 모두 만족하면 출시합니다.

- 위험 등록부에 `미해결` 상태의 높음 등급 항목이 없음
- 결제·재고 필수 테스트 시나리오가 CI에서 통과함
- 배포, 롤백, 백업 복구를 실제로 수행해 봄
- 장애 알림을 받고 대응할 담당자와 절차가 정해져 있음
- 개인정보 처리, 전자상거래 관련 법적 요건을 담당자가 검토함

## 5. 결정이 필요한 사항

| 항목 | 내용 | 기본안 |
| --- | --- | --- |
| 목표 수치 | 1절의 가정치 확정 | 가정치 유지 |
| 호스팅 | 앱, MySQL, Redis 운영 환경 | 관리형 DB·Redis 사용 |
| 0원 주문 (R-07) | 포인트·쿠폰으로 전액 결제 시 처리 | PG 없이 즉시 결제 완료 |
| 환불 실행 주체 (R-08) | 승인 후 누가 환불을 실행할지 | 관리자 승인 시 자동 실행 |
| 리뷰 자격 (R-09) | 구매자만 작성 가능한지 | 구매 확정 고객만 허용 |
| 구매 제한 (R-10) | `itemLimit`이 주문당인지 회원당인지 | 회원당 누적 |
| 반품 정책 | 배송 후 반품·교환 지원 여부 | 구매 확정 전까지 지원 |
| 구매 확정 | 자동 확정 기간 (통계는 `COMPLETED` 주문만 집계) | 배송 완료 7일 후 자동 확정 |
| 채팅 브로커 | 다중 인스턴스 대응 방식 | 외부 STOMP 브로커 또는 Redis 중계 |

기본안은 검토용 제안이며, 결정 전까지 구현하지 않습니다.
